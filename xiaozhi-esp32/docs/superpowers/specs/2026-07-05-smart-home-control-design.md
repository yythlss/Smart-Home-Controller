# 智能家居控制与曲线显示设计说明

## 背景

当前 `bread-compact-wifi` 板型已经完成 TJC/USART HMI 串口屏、DHT11 温湿度、MQ135 空气质量原始值和基础页面事件解析。`page2` 智能家居页已经能向 ESP32 发送设备事件，但固件当前只记录日志，没有实际控制外设。

本阶段目标是在现有工程边界内新增智能家居控制能力，让屏幕按键、语音 MCP 工具和自动模式共用同一套状态与执行逻辑。

## 硬件分配

用户确认当前板上 `GPIO13`、`GPIO14`、`GPIO21`、`GPIO47`、`GPIO48`、`GPIO45` 没有连接任何线。`GPIO47` 原先在固件中定义为触摸/说话按键，`GPIO48` 原先定义为板载状态灯；本阶段允许重新分配。

用户补充的最新 HMI 文件为：

```text
D:/QQ/serial_warm_home  (1).HMI
```

该文件时间戳为 `2026-07-05 16:30:11`，比原记录中的 `D:/QQ/serial_warm_home .HMI` 更新。当前文件被 USART HMI 编辑器或其他进程独占占用，Codex 暂时不能扫描内部控件名、事件字符串和曲线数字 ID。后续如需自动核对 HMI 内部事件，需先关闭编辑器或提供未占用副本。

本设计采用以下分配：

| GPIO | 用途 | 控制方式 | 说明 |
| --- | --- | --- | --- |
| `GPIO13` | 净化器红色 LED | LEDC PWM | LED 亮表示净化开启，亮度表示档位 |
| `GPIO14` | 加湿器蓝色 LED | LEDC PWM | LED 亮表示加湿开启，亮度表示档位 |
| `GPIO21` | 180°角度舵机扇叶 | LEDC PWM，50Hz | 通过角度往复摆动模拟低速、中速、高速风量 |
| `GPIO47` | 备用 | 暂不使用 | 原计划给独立风扇，当前风扇由 `GPIO21` 舵机扇叶控制 |
| `GPIO48` | 备用 | 暂不使用 | 预留给后续状态灯或额外执行器 |
| `GPIO45` | 谨慎备用 | 暂不使用 | ESP32-S3 常见启动相关脚，避免优先使用 |

档位统一按 `0-3`：

| 档位 | 语义 | LED PWM 建议占空比 | 180°舵机扇叶动作 |
| --- | --- | ---: | --- |
| `0` | 关闭 | `0%` | 停在 `0°` |
| `1` | 低档 | `33%` | `20°-70°` 慢速往复摆动 |
| `2` | 中档 | `66%` | `10°-120°` 中速往复摆动 |
| `3` | 高档 | `100%` | `0°-180°` 快速往复摆动 |

当前硬件重新按 `180°角度舵机扇叶` 方案处理。它按 50Hz PWM 脉宽定位角度，后台 `fresh_air_servo` 任务根据 `fresh_air_level` 在不同角度范围内往复摆动。若实物舵机行程偏小、卡住或扇叶打到结构件，只需要调整 `SetServoProfileForLevel()` 的角度范围和步进速度，不需要改屏幕事件、MCP 工具或 HTTP API。

舵机扇叶需要后台任务周期性刷新角度，0 档会停在 `0°`，1-3 档通过不同摆幅和步进间隔模拟低/中/高风量。

180°角度舵机扇叶接线要求：

| 舵机风扇线束 | 连接 |
| --- | --- |
| 信号线，常见为橙/黄线 | `GPIO21` |
| 红色正极 | 外部稳定 `5V` 或开发板可承载的 `5V` |
| 棕/黑负极 | ESP32 `GND` 共地 |

舵机不能由 ESP32 GPIO 供电。若舵机和风扇使用外部电源，外部电源 GND 必须与 ESP32 GND 相连。

## 固件架构

新增一个独立控制器，避免继续把外设控制堆进 `compact_wifi_board.cc`。

建议新增文件：

| 文件 | 职责 |
| --- | --- |
| `main/boards/bread-compact-wifi/smart_home_controller.h` | 定义智能家居状态、控制接口和 MCP 注册接口 |
| `main/boards/bread-compact-wifi/smart_home_controller.cc` | 初始化 PWM、执行屏幕/语音命令、处理自动/节能逻辑 |

`CompactWifiBoard` 只负责创建 `SmartHomeController`，并在三个入口调用它：

1. 屏幕事件入口：`ScreenEventTask()` 收到 `BTN,DEVICE,...` 或 `BTN,MODE,...` 后调用控制器。
2. 传感器入口：`SensorTask()` 每 5 秒读到 DHT11/MQ135 后，把最新环境数据交给控制器做自动判断。
3. MCP 入口：控制器初始化时注册 `self.home.*` 工具，语音控制直接调用控制器方法。

这样屏幕、语音、自动策略都共享一份状态，不会出现“屏幕显示打开但 MCP 查询为关闭”的状态分裂。

## 屏幕事件

现有事件继续保留：

| HMI 事件 | 固件行为 |
| --- | --- |
| `BTN,DEVICE,AIR_PURIFIER,TOGGLE` | 净化器循环：关 -> 1档 -> 2档 -> 3档 -> 关 |
| `BTN,DEVICE,FAN,TOGGLE` | 新风循环：关 -> 1档 -> 2档 -> 3档 -> 关 |
| `BTN,DEVICE,HUMIDIFIER,TOGGLE` | 加湿循环：关 -> 1档 -> 2档 -> 3档 -> 关 |
| `BTN,MODE,AUTO,TOGGLE` | 自动模式开关 |

新增节能事件：

| HMI 事件 | 固件行为 |
| --- | --- |
| `BTN,MODE,ECO,TOGGLE` | 软件节能模式开关 |

需要队友在 HMI 工程中给节能按钮配置：

```text
prints "BTN,MODE,ECO,TOGGLE",0
printh 0a
```

## MCP 语音工具

所有家居控制功能注册到 MCP，供语音控制使用。工具命名统一使用 `self.home.*`：

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `self.home.get_state` | 无 | 返回净化、新风、加湿、自动、节能和最近环境数据 |
| `self.home.set_purifier` | `power: boolean`, `level: integer 0-3` | 设置净化器开关和档位 |
| `self.home.set_fresh_air` | `power: boolean`, `level: integer 0-3` | 设置新风开关和档位 |
| `self.home.set_humidifier` | `power: boolean`, `level: integer 0-3` | 设置加湿器开关和档位 |
| `self.home.set_auto` | `power: boolean` | 开关自动模式 |
| `self.home.set_eco` | `power: boolean` | 开关软件节能模式 |

语义规则：

- 当 `power=false` 时，控制器把对应设备档位强制设为 `0`。
- 当 `power=true` 且 `level=0` 时，控制器自动使用 `1` 档，避免“打开但无输出”。
- 语音打开自动模式时，自动退出节能模式。
- 语音打开节能模式时，关闭自动模式，并关闭净化、新风和加湿。

## 自动模式

自动模式根据最新 DHT11/MQ135 数据做演示级控制。规则先保持简单，便于上板验证：

| 条件 | 动作 |
| --- | --- |
| 湿度 `< 40%` | 加湿开启 `2` 档 |
| 湿度 `> 70%` | 加湿关闭 |
| MQ135 raw `>= 1000` 且 `< 2000` | 净化开启 `2` 档 |
| MQ135 raw `>= 2000` | 净化开启 `3` 档，新风开启 `2` 档 |
| 温度 `> 30°C` | 新风开启 `2` 档 |
| 温度、湿度、空气质量都在正常范围 | 关闭净化、新风、加湿 |

自动模式只在传感器任务提交新数据时评估，当前周期为 `5s`。如果 DHT11 当前失败但固件已有上一组有效读数，自动模式使用缓存读数；如果没有有效温湿度，则只按 MQ135 判断净化/新风。

## 软件节能模式

用户确认本阶段不进入 ESP32-S3 deep sleep，节能模式采用软件节能：

- ESP32 保持运行。
- 语音、MCP、串口屏、传感器采集继续可用。
- 开启节能时关闭自动模式。
- 开启节能时关闭净化、新风、加湿三类执行器。
- 节能开启期间，屏幕手动开启设备或语音开启设备时，自动退出节能模式。
- 自动模式开启时，也自动退出节能模式。

这样可以避免 deep sleep 导致语音、屏幕触摸和联网能力不可用。

## 曲线显示

屏幕需要显示近期空气质量、温度和湿度曲线。TJC 曲线控件通常使用：

```text
add objid,ch,val
```

其中 `objid` 是 HMI 编辑器分配的数字 ID，不是控件名。因此本阶段采用分两步实现：

1. 固件先维护最近 `30` 个采样点的环形历史：温度、湿度、空气评分。
2. 当用户或队友确认 HMI 中曲线控件的数字 ID 后，固件再启用 `add` 命令写入曲线。

建议 HMI 工程新增或确认这些曲线控件：

| 控件名 | 显示内容 | 建议通道 |
| --- | --- | --- |
| `c_air` | 空气评分曲线 | 通道 `0` |
| `c_temp` | 温度曲线 | 通道 `0` |
| `c_humi` | 湿度曲线 | 通道 `0` |

如果 HMI 页面空间不足，可以先只做 `c_air`，温度和湿度后续再加。

需要人工确认：

```text
c_air 数字 ID：
c_temp 数字 ID：
c_humi 数字 ID：
```

在数字 ID 未确认前，固件不发送 `add`，避免写错控件。

当前 `serial_hmi_widgets.json` 里 page2 只有触摸热区，没有设备状态文本。为了让用户看到设备当前状态，建议后续在 HMI 中加入这些文本控件：

| 控件名 | 用途 | 固件示例 |

| `t_purifier` | 净化器状态 | `t_purifier.txt="净化 2档"` |
| `t_fresh` | 新风状态 | `t_fresh.txt="新风 1档"` |
| `t_humid` | 加湿状态 | `t_humid.txt="加湿 关"` |
| `t_auto` | 自动模式状态 | `t_auto.txt="自动 开"` |

这些控件不是第一阶段硬性依赖。第一阶段可以先通过外设动作和 monitor 日志验收。

## 验证标准

第一阶段验收：

- 点击屏幕净化按钮，红色 LED 按 `关 -> 低 -> 中 -> 高 -> 关` 循环变化。
- 点击屏幕新风按钮，连续旋转舵机风扇按 `关 -> 低速连续旋转 -> 中速连续旋转 -> 高速连续旋转 -> 关` 循环变化。
- 点击屏幕加湿按钮，蓝色 LED 按 `关 -> 低 -> 中 -> 高 -> 关` 循环变化。
- 点击自动按钮，自动模式开关正确；开启自动时节能模式退出。
- 点击节能按钮，自动模式关闭，三类执行器关闭。
- 通过语音触发 MCP 工具时，外设动作与屏幕按键一致。

第二阶段验收：

- 最近空气评分、温度、湿度进入历史缓存。
- HMI 曲线控件数字 ID 确认后，屏幕能显示新采样点。
- 曲线刷新不造成整页闪烁或页面回初始态。

## 待人工确认

- 队友最新 HMI 文件中是否已经有节能按钮；如果有，需配置 `BTN,MODE,ECO,TOGGLE`。
- 曲线控件是否已经创建，以及 `c_air`、`c_temp`、`c_humi` 的数字 ID。
- 连续旋转舵机风扇的中位停止脉宽和三个转速档位需要实机校准；若 `1500us` 仍缓慢转动，应微调停止脉宽，若低档不能启动，应适当提高 `1600us`。
- 红色/蓝色 LED 是否串联限流电阻。

## 设计结论

采用 `SmartHomeController` 统一管理智能家居状态和外设执行。屏幕事件、MCP 语音控制和自动模式都调用该控制器。第一阶段先实现三类设备、自动模式、软件节能和 MCP 工具；曲线显示先准备历史缓存，等 HMI 曲线控件数字 ID 确认后再启用实际 `add` 命令。
